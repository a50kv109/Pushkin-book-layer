# Технико-экономическое исследование: Предоставление ИИ-агентам программного доступа к Пушкинской Рифменной Машине

**Дата анализа:** Ноябрь 2026  
**Целевой проект:** Pushkin Rhyme Machine (v2.0)  
**Статус:** Исследование завершено. Архитектурная совместимость подтверждена.

---

## 1. Исследование текущей кодовой базы

### 1.1. Выявление ядра логики
В результате анализа компонентов установлено:
- **UI-слой (`App.tsx`, `components/`):** Отвечает исключительно за ввод текста пользователем, отображение стилизованного пергамента и искусственную задержку анимации (`runSimulation`), имитирующую последовательные этапы работы механического привода.
- **Ядро рифмования (`services/geminiService.ts`):** Функция `transformText(text: string): Promise<TransformationResult>`.
  - Является чистой асинхронной функцией.
  - Не зависит от React-хуков, браузерного DOM или оконных событий.
  - Принимает обычную строку (`string`) и возвращает строго типизированный объект `TransformationResult` (`{ poem, moral, originalText }`).

### 1.2. Вывод о независимости вызова
Функция `transformText` **уже полностью изолирована** от интерфейса представления. Она может быть импортирована и выполнена в любой среде Node.js / TypeScript (серверный процесс, CLI-скрипт, контроллер REST API или обработчик MCP).

## 2. Архитектура интеграции с внешними агентами

Для подключения внешних агентов (ChatGPT, Gemini, DeepSeek, локальные оркестраторы) не требуется изменять существующий код интерфейса. Рекомендуется многоуровневая структура:

```
[Внешний ИИ-агент]
       │ (JSON-RPC / HTTP POST)
       ▼
┌──────────────────────────────────────────────┐
│  Слой интеграции (Agent Gateway)             │
│  ├── Request Validator (проверка лимитов)    │
│  ├── Auth & Rate Limiter                     │
│  └── Router (REST / MCP)                     │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│  Адаптер рифмования (Rhyme Engine Adapter)    │
│  └── services/geminiService.ts               │
│      └── transformText()                     │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│  Форматирование ответа (Response Formatter)  │
│  └── JSON с полями poem, moral, metadata     │
└──────────────────────────────────────────────┘
```

## 3. Анализ предложенных инструментов

| Инструмент | Статус в коде | Описание и готовность |
| :--- | :--- | :--- |
| `generate_rhyme` | **Готов к экспорту** | Прямое проксирование вызова `transformText(text)`. Преобразует входную прозу в поэтическую форму. |
| `generate_poem` | **Готов к экспорту** | Семантический синоним или расширение `generate_rhyme` с дополнительным указанием темы/затравки. |
| `analyze_rhyme` | **Отсутствует в коде** | В текущей кодовой базе анализ рифмы (проверка метра, классификация рифм) является лишь текстовым описанием шагов визуализатора. Для предоставления агенту потребуется отдельный промпт или алгоритмический парсер. |
| `get_engine_info` | **Готов к экспорту** | Возвращает метаданные движка, список этапов из `constants.tsx` (`ENGINE_STEPS`) и правила стиля (ямб, перекрестная рифма ABAB). |

## 4. Сравнение протоколов доступа (REST vs MCP)

1. **REST API (Express / Hono / Fastify):**
   - *Плюсы:* Универсальность, доступность из любых языков программирования (Python, cURL, Go), простота интеграции с вебхуками и кастомными ассистентами.
   - *Минусы:* Агенту требуется отдельное описание OpenAPI/Swagger схемы для вызова.

2. **Model Context Protocol (MCP Server):**
   - *Плюсы:* Нативный современный стандарт для ИИ-агентов (Claude Desktop, Cursor, агентные фреймворки). Агент автоматически обнаруживает доступные функции (`tools/list`) и их JSON-схемы.
   - *Минусы:* Специфичен для экосистем, поддерживающих протокол MCP.

**Рекомендация:** Реализация гибридного или модульного адаптера, где общая сервисная логика доступна как через локальный MCP-сервер (stdio/SSE), так и через эндпоинты HTTP.

## 5. Выводы аудита возможности интеграции

1. Переписывать приложение **не требуется**.
2. React-приложение и визуализатор остаются полностью работоспособными.
3. Достаточно добавить отдельный входной модуль адаптера, не модифицируя существующие файлы `App.tsx` и `components/`.
